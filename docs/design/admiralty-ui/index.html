Admiralty redesign

claude-nimitz 0.3.1 (dev 702afc5) · 2026-10-05 · four design directions, judged against btop: titled panels, few colours with one meaning each, right-aligned numbers, hints in borders, strong focus. Mockups use the real HOME and MAIN fleets; where a mockup needed a busy or blocked member to show a state, its caption says the row was altered. Nothing is implemented yet.

Recommendation: the "command deck"

One coherent design built from the best of each direction:

  1. Layout (direction 1, layout C). A top deck: the fleet panel (admiral, live gauge, counts) and one chip per squadron with a roster gauge (one cell per member, by status). Below it, one member list with squadron header rows instead of boxes inside boxes; runs of not-started members fold into one dim line (flagged members never fold). On the right, a NEEDS YOU panel (only when someone needs you), an ISSUES panel and the DETAIL panel. All of MAIN (10 squadrons, 40 members) fits on 180×48 with rows to spare; at 100×32 quiet squadrons fold to their header.
  2. Rows (direction 3, compact grammar). One status glyph column that merges session status and the herdr pane state (shape and colour both carry it: ◆ ● ○ × · ?), a flag column (▲ error, △ warning, ↺ legacy), short names inside a squadron (DEV, not [MAIN.LUX]-DEV, unless the name drifted), no KIND column, right-aligned ages, fixed count slots. MAIN goes from 62 lines to about 31.
  3. Colour (direction 2, theme B "muted"). Five hues, one meaning each: needs-you, error, warning, busy, and one accent for focus and key hints. Everything else is neutral, with emphasis by brightness. No tinted bands, no gold or purple frames; needs-you is the only filled chip on screen. A Theme of 13 tokens replaces the direct colour constants, with a 256-colour fallback.
  4. Interaction (direction 4). A visible focus model (the focused panel's border and title in the accent), key hints inside each panel's bottom border and specific to the selected row, toasts in the status line so hints never vanish, one letter per action everywhere, ! focuses NEEDS YOU and ⏎ there attaches at once (no confirm: attaching changes nothing), and a confirm dialog with a verb badge, an EFFECT line, numbered steps and long prompts collapsed.

Phasing (each step ships on its own)

  1. Fix-now bugs (below): small, independent of the direction.
  2. Colour tokens and theme B.
  3. Row grammar (status and flag columns, short names, folding).
  4. Command-deck layout and squadron chips.
  5. Focus model, hints in borders, NEEDS YOU panel, new confirm dialog. The NEEDS YOU panel reads the notice files (NIMITZ_STATE/needs/) that the notify hook already writes, so it shows the full question; answering from it waits for nimitz answer.

Fix now (bugs the audits found, whatever direction is picked)

  • False key hints. The detail pane advertises the action-menu letters (s stop, r relaunch, w sweep, d adopt) but on the main screen s switches the split and the others do nothing (detail.rs actions block vs app.rs handle_key).
  • Swapped meanings. Pane dots use yellow for working and green for idle; status uses green for busy and yellow for idle (theme.rs).
  • Invisible on the cursor band. Dim text on the selection colour is 1.01:1, so counts like o30 and separators disappear on a selected band (frames.rs selectable() skips bands).
  • Needs-you is the weakest hue. Pink is 3.93:1 on the background and 1.87:1 on the cursor row; every other status hue is above 5:1.
  • One issue, two colours. An info issue (e.g. rules.old) is cyan on its row but counted as a warning on its band, and the status bar does not count it.
  • Errors and warnings share one glyph; zero counts are dropped so band slots shift; the stowaway band is needs-you pink even with nothing live.

Direction 1: layout and information hierarchy (btop-style panels)

Idea. Stop drawing a box inside a box inside a box. Use one titled panel per job, as btop does: the fleet, its squadrons, the members, what needs you, the issues and the detail. Titles, counts and key hints go in the panel borders. Attention (needs you, errors) gets a fixed place on screen that never scrolls away. Dormant config (29 of MAIN's 40 members are not started) folds into one dim line per squadron.

Data. The MAIN roster, ages, pane ids, the three legacy issues, the stowaways, LUX/DEV's session and the HOME counts all come from status.json. A small overlay exercises the attention paths, since MAIN was calm when it was captured: [MAIN.ARGOS]-COMMODORE busy 2m (really idle 14m), [MAIN.LUX]-DEV needs you 3m, waitingFor "permission prompt" (really idle 10m), and a folder.missing error on [MAIN.ROVER]-OVERT. The overlay uses only fields nimitz already produces (waiting_for, reasons, Issue). Palette: the current mono theme, unchanged. This direction is about structure, not colour. Icons: ASCII mode (@ & S, ! * - x o ?, ^ error, L legacy).

What changes

  • Panels, not nested frames. There is one rounded box per panel. The top border carries the title and its counts, and the bottom border carries that panel's keys. Squadrons become tinted header rows inside a single members panel. The nested frames cost 2 rows and 2 columns per squadron, so this frees 20 rows on MAIN.
  • Top deck. A fleet panel shows the admiral, a stacked live gauge (needs / busy / idle / not started) and the status counts. A squadrons panel shows one chip per squadron with a state glyph, a gauge with one cell per member, sorted needs > busy > idle > not started, and live/total.
  • Needs you is a persistent panel at the top right, with a pink border when it holds anything. An issues panel sits below it and the detail panel fills the rest. ! and i still open the full modals with fixes.
  • Dormant runs fold. Not-started members with no issue collapse into one dim line: o ARGOS BRIM SIGNAL BARK NICKEL 5 not started. Flagged members (needs you, busy, any error) never fold. l unfolds the line.
  • Short names in the tree. The tree shows DEV, not [MAIN.LUX]-DEV, because the header row above already gives the context. The full name appears where context is missing: the needs-you panel, the detail title and the issues list.
  • Fewer columns. NAME, STATUS, AGE (right-aligned) and DETAIL. KIND goes, because the icon and indent already say it. Pane id, session id, pid, cwd and labels move to detail only.
  • Chrome. Each tab gets a dot in its fleet's state colour. The key bar goes, because the hints now live in the borders. The ADMIRALTY status bar stays at the bottom with ? help and q quit on its right, which frees one more row.
  • Narrow (100x32). Panels stack. Quiet squadrons fold to their header row, with the commodore merged in. Open squadrons show only flagged members. The detail is cut to 5 compact lines.

Tradeoffs

ProsCons
A: dashboard + table Closest to today's code (table plus bands). Every column is visible. The gauges answer "how much is running" at a glance. MAIN does not fit: 24 of 52 rows. KIND, PANE and SESSION are mostly empty (1 of 40 members has a short id). Needs you is still a modal you must remember to open. The meter panel repeats counts the bands already show.
B: squadron grid All 40 members visible with no scrolling. Spatial memory: LUX always sits in the same place. The border colour gives the squadron state for free. The masonry leaves dead space (about 10 rows at the bottom left). Crew, task or job rows grow a box and reflow the grid, so the screen jumps. Below about 120 columns it falls back to one long column. Each of the 29 not-started members still costs a row. j/k across columns is ambiguous.
C: command deck Attention has a fixed place and never scrolls away. MAIN fits with room to spare. Dormant config costs one row per squadron. It keeps today's tree model, so j/k, h/l, filters and saved folds all still work. It degrades by folding, not by reflowing. Folding hides dormant ships as rows until l (their names stay on the fold line). Needs you shows twice (panel and row) by design. It has four boxes of border chrome. The squadron chips partly repeat the header-row counts. They earn their place as jump targets (⏎), and they are the first thing to drop when height is short.

Recommendation

  • Adopt C. In order of value: (1) replace the nested squadron frames with tinted header rows in one members panel; (2) add the persistent needs-you and issues panels above the detail, and keep the !/i modals for full lists and fixes; (3) fold dormant runs, but never a flagged member; (4) use short names in the tree and drop the KIND column; (5) put key hints in the panel borders and drop the key bar; (6) add the fleet gauge, with the squadron chips as optional.
  • Breakpoints. Use a side column at width ≥ 150 (today's threshold) and stack below it. Under 40 rows, drop the squadron chips. Under 34 rows, needs you shrinks to one line. Under 100 columns, quiet squadrons auto-fold (the 100x32 mockup). An empty needs-you panel shrinks to its border, showing needs you 0.
  • Do not adopt B's grid (reflow and navigation problems), A's per-status meter panel (it repeats the fleet gauge), or sorting squadrons by state, which would move rows under the cursor. Config order stays, and the needs-you panel provides the priority order.
  • Where it lands. render.rs draw() becomes vertical [tabs 1, deck 6, body, status 1], the body horizontal [members, right 68], and the right column vertical [needs Length(n+2) capped, issues Length(k+2) capped, detail Fill]. In view.rs, squadron_node emits a new dormant-run node. In frames.rs, the band frame drawing becomes a tinted header row.

  • No tinted bands, no gold or purple frames. Every band sits on one raised neutral background (bg1) and every frame uses line. The one exception is a squadron that holds a needs-you session: its frame takes the needs-you hue, so you can find it while scrolling.
  • Needs-you is the only filled chip on screen, in the status cell and in the status-bar count. A filled chip catches the eye at the edge of vision whatever its luminance.
  • Severity ramp: warning, then error, then needs-you. The band counts "others" as warnings only, and info issues stay muted.
  • Pane dots reuse the status hues: working uses the busy hue, blocked uses the needs-you hue, and idle and done stay neutral.
  • Selection: a neutral sel background plus accent corners on the cursor row. Faint and muted text is lifted on bands too, not only on rows.
  • Code: a Theme struct of these 13 tokens replaces the mono::* constants at about 150 call sites. A second theme, the 256-colour fallback and the light fallback then each become a table swap.

How it degrades

  • 256-colour terminals. Today admiralty sends only 24-bit RGB colour codes and never checks COLORTERM. Terminals without truecolor (older macOS Terminal.app, tmux without Tc, some SSH paths) then pick a nearby colour on their own, or garble it. Proposal: if COLORTERM is not truecolor or 24bit, use Color::Indexed from the 256 column above. The ratios hold: A's faint becomes index 244 (3.8:1), needs-you 204 (5.2:1) and accent 81 (9.1:1). B's selection loses its blue cast (it maps to 237, grey) but stays 1.5x brighter than bg0, and the accent corners still mark the cursor.
  • 16 colours or NO_COLOR. Hues drop out, so the meaning must survive in shape. Needs-you is drawn in reverse video and bold, errors bold, faint as the terminal's dim attribute, and the cursor row in reverse. Status glyphs (! * - x o ?) and the words already carry the state, so nothing is lost.
  • Light terminals. Admiralty paints its own background (render.rs:42), so a light terminal profile does not break it today; it simply stays dark. If it ever moves to the terminal's own background (btop's theme_background=False), it needs a light token set. Hues must be darkened to keep 4.5:1, as below. Faint at 3.6:1 is the floor.
faint 3.6muted 5.9fg 12.7strong 17.9busy 5.2warn 5.7error 5.4accent 5.6 ! needs you 5.5

Tradeoffs

  • Pro: the eye goes to needs-you first, then errors, then busy, and everything quiet looks quiet. A screen of idle squadrons turns mostly grey, which is correct.
  • Pro: every text pair is at or above 3.8:1, and body text at or above 4.5:1. The invisible "o30" bug goes away along with the tints.
  • Pro: semantic tokens make a theme, a 256 fallback and NO_COLOR a table each, not 150 edits.
  • Con: the role colours go. Gold no longer marks the admiral and cyan no longer marks commodores, so you rely on the icon, the indent and the KIND column. With Nerd Font icons this is fine. In ASCII mode, @ and & are weaker cues.
  • Con: the screen loses personality. Monokai's look is part of why it felt like a tool you own. Theme A keeps the warmth but not the confetti.
  • Con: in Theme A, error is orange, which some people read as a warning. Theme B fixes this with a true red, at the cost of the Monokai identity.
  • Risk: needs-you text on sel drops to 3.1:1 (A) and 4.4:1 (B). The chip avoids this in the status cell, but needs-you text in the DETAIL column of a selected row is weaker.

Recommendation

  • Adopt now, whatever layout direction wins: the five-hue semantic map, the four brightness steps, neutral frames and bands, needs-you as the only chip, pane dots aligned with status, and the selection lift on bands. These fix concrete bugs (1.01:1 counts, swapped dot hues, info counted as warning) and do not depend on the layout.
  • Default palette: Theme B (muted, btop-like). It is what "clarity like btop" asks for: neutral chrome, a conventional red, and a magenta needs-you that never looks like an error. Ship Theme A as ADMIRALTY_THEME=monokai for anyone who wants the old warmth.
  • Add capability detection (truecolor, then 256, then 16 or NO_COLOR) when the Theme struct lands. It costs one table per theme.
  • Do not keep fleet-state tints, even subtle ones. They are what makes the idle fleet the loudest thing on screen. Do not add hue gradients or meters for status counts either: the counts are small integers, and right-aligned numbers in their status hue are enough.

3 · Status glyphs, row design and density

Palette: the current monokai mono set, with one change. Idle becomes CYAN (it was YELLOW). That matches the idle colour fleet and squadron bands already use (FleetState::Idle). Status glyphs are plain Unicode shapes in both icon modes, so they render without a Nerd Font. Nerd Font glyphs stay for role icons only.

Audit: what the row spends its columns on today

  • Two status channels with swapped colours. The herdr pane dot (theme.rs pane_color) is yellow for working and green for idle. The status word (status_color) is green for busy and yellow for idle. They sit four cells apart on the same row and mean nearly the same thing.
  • Errors and warnings share one glyph. In ASCII mode both are ^; with Nerd Font both are the warning triangle. Only colour separates them, in the row gutter and in band counts. The live capture's MAIN band reads ^2 / ^10 / -10 / o30.
  • Band counts move around. status_counts drops zero counts, so the same slot holds a different status in each band and nothing lines up down the screen. Reading !2 / *3 / -2 / x1 also needs the legend.
  • KIND says nothing new. It is a 10-column word that repeats the role icon, and the frame and position already tell you the role. The commodore is always first in a squadron frame, and every stowaway row says stowaway.
  • The name prefix fills the NAME column. Inside the ARGOS frame, every name starts with the 13 characters [MAIN.ARGOS]-. At 100 columns the tender becomes [MAIN.ARGOS]-COMMODORE/ingest-l…, so the part that tells it apart is the part that gets cut.
  • DETAIL is mostly boilerplate. In the live MAIN list, 27 rows say no session, no lineage and 10 say session file: status idle. Both repeat the STATUS cell.
  • Too few rows on screen. MAIN has 40 members, and 30 of them are not started. Each costs a full line, and each squadron box costs 2 more (band and bottom border). The MAIN frame is 62 lines tall, so a 180×40 screen shows about 5 of its 10 squadrons.
  • The gutter is wide and mostly empty. Pane dot (2), issue mark (2), tree, fold (2) and icon (2) take 8 or more columns before the name, and on most rows 3 of those cells are blank.
  • The list gets 111 of 180 columns. body_areas gives the list 62% at 180 columns. The columns come out as NAME 40, STATUS 14, AGE 5, KIND 10, DETAIL 34, and about half of NAME is prefix.

What changes

  • One status column. A 1-cell glyph whose shape and colour both carry the state: ◆ ● ○ × · ?. When the session status and herdr's pane state differ, it shows the more urgent of the two. herdr blocked counts as needs you, working as busy, done and idle as idle. The separate pane dot goes away.
  • One flag column right after it: ▲ error, △ warning, ↺ legacy, i info. Scanning the left two cells down the screen shows everything that needs attention.
  • Pane presence becomes data. At 150 columns and up, a right-aligned PANE column shows herdr's pane id (w6:p1), or bg for a background session with no pane. Below 150, the status glyph sits on a lit cell (BG_HI) when ⏎ can jump to its pane.
  • Short names. Strip [FLEET.SQUADRON]- only when the session name starts with the frame's prefix. A drifted name stays visible (ANVIL-2, in orange). Stowaways keep their full names, because there the prefix is the information.
  • No KIND column. Ships, the default role, get no icon. Every other role keeps one: ★ ✦ ⊕ » ‡ ⊘ ∅.
  • Numbers line up. AGE is right-aligned, and its colour fades with age (s and m bright, h soft, d dim). CREW is running/total. TASKS is a 4-cell meter plus done/total. A column is drawn only when some visible row has data for it.
  • btop-style meters. Each squadron heading carries a roster strip, one status glyph per member in chain-of-command order (○·····), plus live/total. The fleet band has fixed count slots (zeros dim, never dropped) and a 12-cell stacked meter. A needs-you row gets a 1-cell wait ramp ▁▃▅▇ next to its age, on a log scale from 1 minute to 4 hours.

Tradeoffs

  • Compact, for: MAIN drops from 62 to 31 lines and fits a 180×40 screen alongside the detail pane. The left two cells carry state and trouble. Numbers and count slots line up. One status colour scale, so pane and status can no longer contradict each other on screen. No new data needed: every cell comes from Member, SessionInfo, Crew, Task or herdr panes.
  • Compact, against: The roll-up row puts dormant ships one l away, so "start just SIGNAL" takes an extra keypress. Columns that appear only when there is data can shift the layout when you switch tabs; pinning them per fleet would fix that. Merging herdr and session state hides their disagreements unless the detail pane states them (it should print both). Recolouring idle from yellow to cyan breaks existing habits.
  • Cards, for: The best fleet overview: a squadron reads as a unit, the roster strip gives you its shape at a glance, and the whole of MAIN fits in 19 lines at 180 columns.
  • Cards, against: Moving through a grid is two-dimensional, and h/l already mean fold. Card rows waste space when squadron sizes differ (the ROVER row). Crew trees and long DETAIL text do not fit in a 56-column card. At 100 columns only 2 cards fit per row, and DETAIL shrinks to about 12 columns. The detail pane has to become a drawer.

Recommendation

  • Adopt the compact grammar as the default list: the status and flag columns with the merge rule, idle in CYAN, prefix stripping, no KIND, PANE column or lit cell, quieter DETAIL, fixed count slots with zeros dim, roster strip, dormant roll-up, unboxed squadron headings, and 2-column tree guides.
  • Treat cards as a later, optional overview (for example a key that switches list and cards) for big fleets like MAIN. Do not make it the default: navigation and crew trees fit the list better.
  • Do not adopt animated spinners (the refresh interval is too slow to animate them well), age bars on every row (only the needs-you wait ramp is worth it), or folding the commodore into the squadron heading (their actions differ).

4 · Interaction, focus and discoverability

Palette: the current monokai mono set, unchanged. The one new rule: gold marks where your keys go. The focused panel gets a gold border and a gold title badge, and its selected row gets a gold ▌ bar on SEL. Other panels have DIM borders, and their selected row keeps only a BG_HI ghost. Status colours keep their meaning: pink needs you, green busy, yellow idle.

What the audit found (code, not taste)

  • The detail pane lists keys that do something else. detail.rs actions_block prints each act with Act::key(), and those are the letters inside the x menu. On the main screen, app.rs handle_key binds only a u A D x. So the detail pane says s stop, but s sets split-below. It says w sweep, r relaunch and d adopt, but those keys are unbound. And x rm opens the menu instead. The STOWAWAYS band text ("d adopt it…, x rm its job row") has the same problem.
  • Some letters change meaning by layer. x is the menu, but rm inside the menu. s is split, but stop in the menu. a is start, but "all" in the fleet filter. y is yank, but run in confirm and yank-fix in issues.
  • Only the list ever takes focus. The detail pane scrolls only with ctrl-e/ctrl-y. You can't select or yank its issue fixes or ACTIONS lines.
  • Hints disappear when you act. render.rs bottom_line swaps the key bar for a toast or the busy line for 8 s, which is exactly when you need the hints. The 14 hints are global, so a start still shows on a member that is already running.
  • Getting from needs-you to the session takes 5 keys and a plan. The flow is ! → j → ⏎, and ⏎ only reveals the row and closes the modal. Then A → read the confirm → y. A background ship has no pane, so ⏎ on its row only says "no pane hosts this session". The modal shows name, age and one line. Admiralty never reads NIMITZ_STATE/needs/<id>.json (core notify::read), which holds the full question with its options, the kind, and whether the commodore was told (delivery is pending, delivered or failed).
  • The confirm dialog buries the decision. A ship start carries its whole prompt and settings JSON. For start MAIN/ROVER/SILGAP that is a 1,535-char prompt plus about 220 chars of labels, roughly 17 wrapped lines. The legacy warning that should change your choice (adopt the old session instead) gets the same weight as all of that.

  • Three panels you can focus: FLEET (the list), NEEDS YOU (shown only when the count is above 0) and DETAIL. tab/shift-tab cycles focus. Fleets move to [ ], and 1-9 still jump to a fleet. The fleet tabs sit in the FLEET panel's top border, which saves the tab line.
  • Key hints live in the focused panel's bottom border, worked out for the selected row: only keys that are open there, and the row's name as a badge. An unfocused panel shows just tab focus here. The status line keeps only the global keys (! i / ? q). A toast goes in the status line's middle and never covers a hint.
  • Each letter means one thing everywhere. Every action letter works on the list, in the detail ACTIONS, and in the x menu: a start, A attach, s stop, r relaunch, w sweep, X rm, d adopt, D remove from config, m message, e edit. v toggles the split, which frees s. x stays as the full menu.
  • A focused DETAIL panel has its own cursor: j/k moves over ACTIONS lines and issue fixes, ⏎ runs one, and y yanks a fix.
  • NEEDS YOU becomes a panel, not a modal. It sits on top of the right column, lists oldest first across all fleets, and shows whether the commodore was told. ! focuses it from anywhere. On a need: ⏎ attaches straight away (background ship: claude attach in a new pane, with no confirm, since attaching changes no state) or jumps to the blocked pane. 1-9 and t answer through nimitz answer once it lands. g shows the row. A permission request never gets a one-key allow.
  • The confirm dialog reads top-down: the verb as a coloured badge (green starts/opens, orange stops/relaunches, pink rm/remove/refused), an EFFECT line of counts, then any warning that has an action key (d adopt instead), then numbered steps with where each one runs. The prompt and settings collapse to ‹…›, and v expands them. The keys sit in the bottom border, with ⏎ to run. A refusal has no run key at all.

Tradeoffs

  • + You can see at a glance where your keys go, as in btop. Hints sit next to what they act on, and they never lie (every key shown works there).
  • + Needs-you to attached takes 2 keys (! ⏎), not 5 plus a plan. Questions can be answered in place once nimitz answer exists.
  • + No core changes. The only new input is reading NIMITZ_STATE/needs/*.json through core's notify::read.
  • − tab just shipped as next-fleet in 0.3.1, so this breaks fresh muscle memory. 1-9 still jump straight to a fleet.
  • − Direct s r w X d put state changes one key away. Each still opens the confirm-with-plan, so nothing runs on one key, but stray keys open more dialogs.
  • − The NEEDS YOU panel takes 3–7 rows from the detail pane while anything is blocked. Collapsed ‹prompt› hides what will be typed, so v has to stay visible in the border.

Recommendation

  • Fix the false hints now, whatever else is chosen: map s r w d (and X for rm) as direct keys, move split to v as a toggle, and drop d/x from the STOWAWAYS text. It's a small, contained diff.
  • Adopt: the gold focus model, hints in panel borders (context-sensitive for the focused row), toasts that never cover hints, the NEEDS YOU panel reading the notice files with ⏎ = attach or jump without a confirm, and the confirm layout (EFFECT line, action keys on warnings, collapsed ‹prompt›, ⏎ to run).
  • Adopt with care: tab for focus and [ ] for fleets. If you'd rather keep tab for fleets, give focus to ctrl-w / ! / esc-back-to-list instead. Everything else stays the same.
  • Not now: one-key answers for permission requests, ever. Also any answer key before nimitz answer exists: show 1-9 dim with "needs nimitz answer" until then.
