## 2. NEW PATHS (found in --help, slash commands, docs; not in my list)

- **`/background` (`/bg`) and `/fork`** inside an interactive member: `/background` "Detach the current session to run as a background agent" (commands.md); `/fork` "Copy the current conversation into a new background session" with SessionStart `source fork` (hooks.md). `/fork` is refused for "Sessions started with launch flags the copy wouldn't inherit, such as a replaced system prompt or a `--tools` allowlist" (agent-view.md). Same family as `←` (R1 inside 3.5): not re-run here (area `inside`).
- **`/branch [name]`**: "copies the transcript and switches the running Claude Code process to write to it" (sessions.md): same pid, **new session id**, SessionStart `fork`; a Remote Control connection "follows you into the branch". A member that runs `/branch` changes its session id in place (same class as `/clear`, R1 G1). Not run.
- **`/desktop` and `claude --desktop --resume <id>`** (macOS/x64 Windows only): moves a conversation into Desktop; "doesn't move a session that is open in another terminal or still running in the background".
- **Deep links** `claude-cli://open?repo=owner/name&q=...` (deep-links.md): opens "a new terminal window with Claude Code running in the directory the link specified" = an unlabelled interactive session in whichever clone of that repo the user last ran `claude` in: a stowaway factory for a ship whose folder is a clone. `vscode://anthropic.claude-code/open?session=<id>` resumes a member's id in the VS Code panel (vs-code.md "Launch a VS Code tab from other tools").
- **Dispatch** (mobile app -> Desktop): spawns Desktop Code sessions "with a Dispatch badge" (desktop.md); Desktop-only.
- **`claude remote-control --spawn worktree`**: every remote connection gets a worktree session (remote-control.md).
- **`claude --bg --exec <cmd>`**: "run a shell command as a background job instead of a Claude session" (cli-reference.md); a job row with no conversation (`daemon status` mentions "exec runs never respawn").
- **Desktop local scheduled tasks and Dispatch sessions** start fresh sessions in a folder on a timer (desktop-scheduled-tasks.md).
- **`CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1`** (env-vars.md): "Used in SDK mode so the model continues without requiring the SDK to re-send the prompt"; a host that sets it makes a resumed member run a turn on its own.
- **Session file `entrypoint`** (undocumented field; documented values for the metrics attribute: `cli`, `sdk-cli`, `sdk-ts`, `sdk-py`, `claude-vscode`, `claude-in-slack`, `claude-desktop`, `claude-desktop-3p`, `local-agent`, monitoring-usage.md `app.entrypoint`): the one field that tells the surfaces apart. nimitz does not read it (`grep -r entrypoint crates/` is empty).

## 3. GAPS

**remote-G1. A nimitz relaunch silently reconnects Remote Control on a background ship (BREAK, high, safety).**
Trigger: anyone once ran the member's conversation with `--remote-control`/`/remote-control` (by hand, from VS Code, from Desktop), then `nz start`/`relaunch`, a daemon crash-restart, idle wake or upgrade adopt resumes it.
What breaks: the ship is listed and steerable at claude.ai/code and in the mobile app ("Continue here, on your phone, or at https://claude.ai/code/session_01EXAMPLE..."), its transcript is "stored on Anthropic servers" while connected (remote-control.md "Connection and security"), and nimitz shows `idle`, `check: no errors`. Prompts from the phone land in the ship with no commodore in the loop.
Evidence: R-5; `claude logs c08c51bd` `/rc connecting…` -> `/rc`; attach + `/remote-control` panel text; transcript `remote_session_change` with the URL; docs quoted in R-5.
Repro (fresh world, ship started by `nz start F/SQ/S1`, then `nz stop F/SQ/S1 --yes`):
```
cd <ship dir> && claude --resume <sid> --name '[F.SQ]-S1' --settings '<labels json>' --remote-control RC-TEST   # in tmux; wait for "/rc active"; type /exit
nz start F/SQ/S1 --yes; sleep 20; claude logs <short> | grep -o '/rc[a-z …]*'      # shows /rc
grep -o '"type":"remote_session_change"[^}]*' ~/.claude/projects/<proj>/<sid>.jsonl  # URL recorded

```
Fix seen to work: `claude attach <short>` -> `/remote-control` -> "Disconnect this session" (writes `remote_session_change` `"url":null`); a later stop + `nz start` stays off. nimitz could read the last `remote_session_change` in the transcript (url set = exposed) and raise `remote.exposed` with that fix, or run the disconnect itself before a relaunch.

**remote-G2. A member run by another surface (SDK host, Remote Control terminal, IDE panel, Desktop) with its labels looks healthy and is not controllable (GAP, med).**
Trigger: `--resume <member sid>` with the labels from an SDK host (R-12), from `--remote-control` (R-4), inferred for VS Code/Desktop (R-1, R-3).

## 4. Why the job-row design (Part 2)

### 4.1 What the docs say (quotes; file = the page's `.md` on code.claude.com)

**The job row and its id.** "Every background session has a short ID you can use from the shell. The ID is printed when you start a session with `claude --bg`, and each session's ID is its directory name under `~/.claude/jobs/`." (agent-view.md "Manage sessions from the shell"). "`~/.claude/jobs/<id>/state.json` Per-session state shown in agent view. Read it through `claude agents --json` instead of parsing the file" and "The files under `~/.claude/jobs/<id>/` are not a stable interface" (agent-view.md "Where state is stored", "Read session state from a script"). "`~/.claude/daemon/roster.json` List of running background sessions, used to reconnect after a restart."

**A job outlives its process.** "The supervisor is a background service that runs your background sessions so they keep working after you close agent view or your terminal." "Each session is its own Claude Code process under the supervisor, and what happens to that process depends on the session's state: Working, paused on a permission prompt or other dialog, or attached: the process keeps running. ... Finished or waiting for your next message, and unattached for about an hour: the supervisor stops the process to free resources. ... The conversation stays on disk, and the next time you attach or reply, the session resumes where it left off. Pin a session with `Ctrl+T` to keep its process running. Exited unexpectedly while the supervisor is running: the supervisor restarts the process. Ending a session you backgrounded yourself with `←` or `/background`, for example with `kill`, marks it stopped instead of restarting it. After an auto-update: the supervisor restarts itself onto the new version and moves idle sessions over in the background. Sessions that are working, waiting on you, or attached aren't interrupted." (agent-view.md "The supervisor process"). "When memory stays low, the supervisor also stops idle sessions to free resources on its own, and stops idle pinned sessions too if stopping the others freed nothing." "A background session that wasn't waiting on your input and is found dead more than 48 hours after its last activity ... shows as stopped with `ended while the background service was off`" (v2.1.248 row). "Sessions are local: ... They are preserved across sleep but stop if the machine shuts down." (Limitations).

**What a restart re-applies (the reason `respawnFlags` exists).** "The permission mode, model, and effort you chose for a background session, along with the configuration flags it carries, all persist when the supervisor later stops and restarts its process." ### 4.2 What I infer from the behaviour (R1 notes + read-only `state.json`, `roster.json`, `daemon.log`)

**Files (read-only, 2026-10-07).** `jobs/<id>/state.json` keys seen across 16 rows: `backend, children, cliVersion, createdAt, cwd, daemonShort, detail, fan, firstTerminalAt, inFlight, intent, lastTerminalAt, linkScanOffset, linkScanPath, name, nameSource, needs, output, providerEnv, respawnFlags, resumeSessionId, sessionId, state, suggestedReply, template, tempo, tokens, updatedAt`. `daemon/roster.json` = `{proto, supervisorPid, updatedAt, workers{<short>: {pid, procStart, sessionId, rendezvousSock, ptySock, cliVersion, startedAt, attempt, cwd, dispatch{proto, short, nonce, sessionId, createdAt, source: shell|fleet, cwd, launch{mode: prompt|resume, args|flagArgs, sessionId, transcriptPath, fork, restoresTranscript}, env, isolation, respawnFlags, seed{intent, name}}, decModes, firedInteractiveMarks, rvAuth, ptyAuth, replPid, replProcStart}}}`. `ptySock` paths are `/tmp/cc-daemon-<uid>/<daemon>/spare/<spareid>.pty.sock`: the pty host a job runs in keeps the id of the spare it was.

**`daemon.log` vocabulary** (551 lines, normalised): `bg spare spawned host pid=N` (109), `bg claimed-spare <id> (shell|fleet|spare|slash)` (90), `bg spawned <id> (shell|slash|spare)` (14), `bg settled <id> (done|killed|crashed[: source session ... not found])` (92), `bg retire <id>: idle-prompt|settled|stale-spare, idle Nm|Nh` (19), `bg orphan-spare reap: N`, `bg adopt: adopted=N respawned=N dead=N`, `bg: post-takeover prewarm burst — respawned 0/N stale workers, N refused`, `[supervisor] binary at ~/.local/bin/claude changed (2.1.290 → 2.1.292) — self-restarting for upgrade`, `shutting down (cause=upgrade|idle_exit, uptime, leases, live_workers)`, `idle 5s with no clients — exiting`, `─── daemon start ─── version=... origin=transient`, auth refresh lines. My ship: `claimed-spare c08c51bd (shell)` on the cold `--bg` launch, `settled c08c51bd (killed)` on each `claude stop`, `claimed-spare c08c51bd (fleet)` on each `nz start` (= `--bg --resume`).

**Inference 1: the process is disposable, so the row is the identity.** A background "session" is never one process: the daemon keeps spares warm (`bg spare spawned host` 109 times; a spare = a pty host plus a booted `claude` with a credential snapshot, cf. changelog 2.1.174), and a dispatch **claims** one (`claimed-spare <id> (shell)` even for a cold `--bg`). The worker's pid, pty socket, `attempt` and even `cliVersion` change over the job's life (2 of 13 live workers are "from a different CLI version", `daemon status`). What stays is the directory `jobs/<short>/`: the attach handle, the agent-view row, the name, and the recipe to rebuild the process. That recipe is `respawnFlags` (+ roster `dispatch.launch{mode, sessionId, transcriptPath, flagArgs}`): every wake, whether `attach`, a reply, a crash restart, `respawn`, the upgrade "prewarm burst" or a retire->wake, replays `--resume <resumeSessionId>` with those flags. This is why R1 saw labels survive stop/start, respawn, `kill -9` and the 2.1.290->2.1.292 adopt, and why `/rename` (which rewrites `respawnFlags` and `state.json.name`) and by-hand flags (which make a copy instead of touching the recipe) are the only ways labels drift.

**Inference 2: `sessionId` vs `resumeSessionId`.** `sessionId` is the id the row was born with (= the short id, the directory name); `resumeSessionId` is the conversation the next wake will load. They differ after `/clear` (R1 inside 3.1c: `sessionId 9cdceb2d`, `resumeSessionId 79519302`, same pid, same row) and would after `/branch` or an in-session `/resume`. The split exists because the row must keep its address while the conversation underneath changes: `claude attach 9cdceb2d` still works after `/clear`, and `claude agents --json` reports the live id while running but the row id once stopped (R1). The docs cover the session side (`/clear` saves the old conversation) and not the row side, which is exactly where nimitz broke (R1 G1/G2: registry keyed by session id, not by job id).

**Inference 3: `respawnFlags` is the launch command minus what must not be replayed.** For a cold launch the roster keeps `launch.args = [--session-id <sid>, --name, --settings, 'reply ok']` and `seed.intent = 'reply ok'`; `respawnFlags` keeps the flags (R1 saw the daemon restart a crashed worker with `--session-id <id> --name ... --settings ...`, SessionStart `startup` only because the transcript was gone). A resume launch stores `launch.mode resume`, `transcriptPath`, `restoresTranscript true` and `flagArgs`. So the row is "how to get this conversation back with the same identity"; the prompt is replayed only when no transcript exists (docs: "when none is on disk, it runs its original prompt again as a new conversation").

**Inference 4: the state machine.** `settled (done)` = turn finished; `settled (killed)` = `claude stop`/kill (row `done`/`stopped`, no auto-restart); `settled (crashed)` = exit without stop (row `crashed`, the pty host restarts it ~11-15 s later, R1 cli 1g, inside 5c-1, with no daemon.log line); `retire <id>: settled|idle-prompt, idle 60m` = the hour rule (R1 inside 5c-3: no SessionEnd hook on retire, row stays, next attach/`nz start` claims a spare for the same id: `claimed-spare 9aacf927 (fleet)`); `retire: stale-spare, idle 61m` = an unclaimed spare is dropped; `orphan-spare reap` = cleanup of hosts whose daemon died. `idle 5s with no clients — exiting` + `cause=idle_exit, live_workers=0`: the supervisor itself exits when nothing is running, so "the service" is also disposable; only `jobs/` and `roster.json` are durable.

**Inference 5: adopt on upgrade.** On a binary change the supervisor logs `self-restarting for upgrade`, `shutting down (cause=upgrade, live_workers=2)`, the new one logs `bg adopt: adopted=2 respawned=0 dead=0` and then `post-takeover prewarm burst — respawned 0/2 stale workers, 2 refused`: it reconnects to still-running workers through the roster (`pid` + `procStart` to detect pid reuse, `rendezvousSock`), does not restart busy or attached ones ("refused"), and moves them to the new binary only when idle (the workers keep `version 2.1.290` in their session files under a 2.1.292 daemon, R1 inside 5b). The roster's "older version preserves unknown fields" rule is what lets a downgrade/upgrade race not lose rows.

**Inference 6: dispatch sources.** `(shell)` = a `claude --bg` from a shell (cold launch, prompt); `(fleet)` = a resume of an existing row (`--bg --resume`, attach-wake, nimitz start: all my `nz start` resumes logged `(fleet)`); `(slash)` = `←`/`/fork`/`/background` from inside a session (R1 inside 3.5: `bg spawned 7e1875a4 (slash)` with `interactiveLineage: true`); `(spare)` = the agent view claiming a draft (`claimed-spare aa26510f (spare)`, `kind bg, spare: true`). The roster field is `dispatch.source` with the same values. The two `1f3d0a1c` claims 5 s apart (`(fleet)` then `(shell)`) show a resume followed by a fresh dispatch on the same short id; I did not chase it (another area's ship).

**Inference 7 (for nimitz).** Key members by **job id** (`daemonShort`, directory name) and treat `resumeSessionId`/the session file's `sessionId` as "the conversation now"; read `respawnFlags` as the authoritative identity (labels, name) and `nameSource`/`name` for drift; expect no hook on retire/crash (use `state`); treat `spare: true` session files and session files with no SessionStart as transient; and, new from this round, read the session file `entrypoint` + `jobId` to tell a member that is "running elsewhere" (sdk-cli, claude-vscode, claude-desktop, an RC terminal) from a real job, and the transcript's last `remote_session_change` to tell an exposed one.
