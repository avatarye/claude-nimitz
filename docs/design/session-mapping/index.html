What 0.4.0 changes

  • One identity, one job. Every member is a Claude Code background job; the registry (v2) anchors an identity on the job and keeps every conversation in its lineage (launch, resume, clear, branch, fork, relaunch, migrate). The SessionStart hook binds every labelled start under the lock.
  • Recovery by exact id. A stopped job wakes by its birth id (the only id Claude Code wakes it by); after a /branch or /resume nimitz removes the row and resumes the conversation the member ran last, with every flag. Never -c, never a resume of a live job. A lost transcript is history.lost with --fresh, never "[OK] verified". A wake that races the daemon is retried once.
  • Leads as background jobs attached in their Herdr tab (claude attach), pinned against idle retire; a lead's folder is exclusive (lead.intruder, one fix per kind); 0.3.x interactive leads migrate by /exit then nimitz start.
  • Stowaway rule v4. In a ship folder an unlabelled session is the user's own unless it is a copy of a ship (shared transcript root, a resume of a lineage id, the ship's name); copies are swept. Spares and pickers are ignored for a grace time; another home's sessions never appear.
  • Live rules (rules v2) delivered on UserPromptSubmit once per version per job, re-delivered at every SessionStart; every member may run nimitz (Bash(nimitz *)), authority by a role table tested over every command; the admiral may message every member of its fleet.
  • nimitz restore from the Herdr shape (herdr api snapshot + pane process-info), with the last-known active set; never types into a pane that runs anything but a plain shell; up and layout herdr share its engine; Admiralty x R.
  • Tenders removed, with migration (retired history, tender.retired). Per-fleet config isolation, conflicted copies, git-root trust, rc.exposed, name.drift, pins kept tidy, a registry that no writer can shrink.

Checks 1 to 5 (the facts the mapping depends on)

1. Is the job id stable?

Yes. The job id (the folder name under ~/.claude/jobs/, the short id) stays the same across stop, kill, respawn, the idle retire and the next nimitz start, a native --bg --resume, /clear and /branch (only the session id moves), a worker crash and the daemon's own restart, and an upgrade adopt. After claude rm, a resume makes a new job named by the short form of the resumed session id: for nimitz's resume that is the same short id again, because nimitz resumes its own session; a by-hand resume of another id gets that id's short form. Only copies (a resume while live or with other flags, a fork, -c) get new job ids.

Evidence: cli Q1, inside Q1, env Q1; verify-cli confirms

2. Does respawnFlags keep the labels and the name?

Yes, through every step above. /rename and Ctrl+R rewrite --name in it (2.1.292: the new name is kept, not removed). claude rm drops the row with its flags; nimitz's resume after an rm passes every flag again, so they come back.

Evidence: cli Q2, env Q1

3. Can a lead be a background job attached in a pane?

Yes. A claude --bg commodore with its labels, attached in a terminal, led an agent team (it spawned a teammate and gave it a task), showed and answered AskUserQuestion, used SendMessage, and ran nimitz status. The docs: an attached session "behaves like any other Claude Code session" (exceptions: /install-github-app, the /mcp list need a person attached). An attached session is never idle-retired; an unattached one is, after about an hour, unless it is pinned. A pin (Ctrl+T) is stored only in ~/.claude/jobs/pins.json; a pinned ship stayed live 64+ idle minutes while an unpinned one retired at 61. Pin by file: it works: ship A, pinned only by an atomic write to pins.json, had no retire line and stayed live, while ship B retired at 60 idle minutes (bg retire f59e1f5f: settled, idle 60m); the agent view listed A as pinned. Claude Code takes pins.json.lock before it writes, so nimitz must take the same lock.

Evidence: inside Q3, env E1-E3, remote Q3, verify-inside

4. Worktrees.

Deferred by the user (ships keep bgIsolation: none). Transcripts and -c: the exact cwd (the project dir name). --resume <id>: the cwd, its worktrees, then every project if only one holds the id. Trust: the git root (else the start folder and below). Why Claude Code uses job rows

What the docs say

  • "Every background session has a short ID ... each session's ID is its directory name under ~/.claude/jobs/." The files there "are not a stable interface"; read state through claude agents --json. (agent-view.md)
  • The supervisor "runs your background sessions so they keep working after you close agent view or your terminal". "Each session is its own Claude Code process under the supervisor": a working, blocked or attached session keeps its process; a finished or waiting one, "unattached for about an hour", is stopped "to free resources" and resumes "where it left off" on the next attach or reply; a pin keeps the process; a crash is restarted; after an auto-update the supervisor "restarts itself onto the new version and moves idle sessions over". (agent-view.md, "The supervisor process")
  • "The permission mode, model, and effort ... along with the configuration flags it carries, all persist when the supervisor later stops and restarts its process" (--settings, --add-dir, --mcp-config ...), and a name set with /rename persists too. (agent-view.md; changelog 2.1.143, 2.1.169, 2.1.202)
  • --resume <id> --bg "either continues that session under the same ID, or starts a copy under a new ID and prints a note:". "Two processes can't write to the same transcript." (agent-view.md)
  • /clear: "start fresh with an empty context. Claude Code saves the previous conversation" (sessions.md); SessionStart source clear (hooks.md); CLAUDE_CODE_SESSION_ID "is updated on /clear" (env-vars.md). What the job row holds after /clear is not documented.

What we infer from the behaviour

  • The process is disposable, so the row is the identity. The daemon keeps warm spare processes and a launch claims one (claimed-spare <id>, even for a cold --bg). The pid, the terminal host and even the Claude Code version of a job change over its life. What stays is jobs/<id>/: the attach handle, the row, the name and the recipe to rebuild the process.
  • respawnFlags is that recipe. Every wake (attach, reply, crash restart, respawn, upgrade, retire then wake) replays --resume <resumeSessionId> with those flags. That is why the labels survive everything except a copy.
  • sessionId is the birth id; resumeSessionId is the conversation now. They split after /clear or /branch: the row keeps its address (claude attach <id> still works) while the conversation under it changes. A conversation is the unit of history; a job is the unit of running work. One job holds one conversation at a time because one process writes one transcript.
  • Why this design (inferred): a session must outlive the terminal, the process and the binary, and must be cheap to stop when idle. A durable row plus a replayable recipe gives all of that; the conversation id stays the history key, as for interactive sessions.

Ships and tenders

Ships must be background jobs and anchor on the job (id, respawnFlags, name, labels); the conversation id is history only, so /clear, a branch and a resume inside the job keep the member. Several ships may share one folder: an unlabelled session in that folder is the user's own work, unless it resumes or forks a ship's conversation. Tenders are removed: one-off work in a lead's own context goes to a subagent, one-off work in a project folder to a ship.

Folder anchor or conversation lineage

Identity ↔ folder + job (one way) fits Claude Code's own model: the job is what Claude Code keeps alive, restarts and adopts, and the folder keys transcripts, -c, trust and settings. Identity ↔ conversation lineage (0.3.1) fails every time the conversation id moves (M1, M2) or two processes share it (M6). 0.4.0 keeps the lineage as history and anchors on the job; for leads the exclusive folder is a second check, not the anchor.

Round 1

Session mapping

claude-nimitz 0.3.1 on Claude Code 2.1.292 (it updated from 2.1.290 during the night) · 2026-10-07 · investigation only: nothing is implemented. Written in ASD-STE100 style, with the words of docs/design/cc-control-model.md §1.

Summary

  • We ran 38 cases on real Claude Code in a throwaway fleet. Result: 18 OK, 11 gaps, 8 breaks, 1 limit.
  • Ship lifecycle commands are safe: stop, kill, rm, respawn, attach and a native resume keep the same session id and the labels. The job row keeps the launch flags (respawnFlags).
  • The mapping breaks when the session id changes under a member (/clear, /resume, ←), when two processes share one id (claude -c next to a live lead), and when nimitz recovers a lead with -c. In these cases nimitz shows a live member as stopped, suggests a fix that stops the real member, or continues the wrong conversation.
  • Case 0: background members stop on their own after about one idle hour. The daemon retires them (bg retire <id>: idle-prompt, idle 61m). No SessionEnd hook fires. This stopped NIMITZ_DEV twice.
  • Root causes in nimitz: the registry moves only on a nimitz action; rows are keyed by session id, not job id; labels are kept per session id, not per process; leads resume with -c; leads started outside a nimitz pane never bind.
  • The design gives ten invariants (I1 to I10). The two most important: every session that starts with an identity's labels joins its lineage (the hook binds, by SessionStart source); and recovery continues the lineage current by id, never with -c.
  • Some gaps cannot be closed because Claude Code does not allow it: no hook can refuse a session, idle retirement has no setting, and a reboot does not respawn. The design detects these and repairs them.

How it works now

Claude Code and nimitz see a session in different ways. Claude Code keys everything by a session id. nimitz keys everything by an identity. The registry connects the two.

Claude Code: one process runs one session id. A job row (background only) can carry several session ids over time.

nimitz: the identity is fixed. The labels and the hooks connect a session to it. The snapshot reads Claude Code's files to find the live state.

Case 0: why a background ship stops on its own

NIMITZ_DEV stopped twice with a Stop line and no SessionEnd. The daemon log gives the cause:

[2026-10-05T07:09:01Z] [bg] bg retire 9aacf927: settled, idle 60m
[2026-10-06T02:18:02Z] [bg] bg retire 9aacf927: idle-prompt, idle 61m
[2026-10-06T02:18:02Z] [bg] bg settled 9aacf927 (done)
  • The daemon stops a background session that is idle at the prompt and not attached for about 60 minutes. The docs confirm it (agent view, "The supervisor process"). The conversation stays on disk.
  • No SessionEnd hook fires for it. The job row goes to done. nimitz shows the member as stopped, with no reason.
  • No setting, variable or flag changes the time. The documented opt-out is a pin (Ctrl+T in agent view). We found no file or command that sets the pin.
  • Other causes: a new binary restarts the daemon, but the daemon adopts the live workers (no stop). A crash restarts in about 15 s. A reboot stops all sessions, and they do not come back by themselves.
  • Recovery works today: nimitz start does a native resume with the same id (this session came back that way). The gap is that nothing does it automatically, and the status does not say why (G11).

Proposed design: one solid identity → session mapping

Goal: the identity is the only thing the user must know. A session is only the identity's current body. nimitz follows every body change, and it repairs every by-hand change, or tells the user the one step that repairs it.

invariantrulehow nimitz enforces or repairs itcloses
I1One identity has one lineage and one current session. Only the registry says which session is the identity.A name, the newest transcript and -c never decide it. All binds go through one writer under the registry lock. Each lineage entry records via: launch, resume, relaunch, clear, compact, fork, adopt or hook.G1, G3, G9
I2Every session that starts with an identity's labels joins that identity's lineage, whatever its SessionStart source.The SessionStart hook binds: startup and resume bind or confirm; clear and fork append and move current; compact confirms. If a hook line is lost, status replays the events under the lock. A lead binds the same way as a ship.G1, G5, G9
I3nimitz keys a background member by its job id, and it keeps labels per process.Join rows by session file jobId and job daemonShort. The live id is the session file sessionId or the job resumeSessionId; the job sessionId is only the launch id. A labelled pid is the member; an unlabelled pid on the same id is an intruder.G1, G2, G4
I4An identity has at most one live process, and a session id has at most one live process.Two live pids for one identity or one session id give dup.live with the exact terminal of each (the session file tmux or Herdr fields). nimitz never merges them.G4
I5Recovery continues the lineage current by its id.Leads and ships resume with --resume <current>; never -c. A resume that comes back with SessionStart startup is a history loss: nimitz raises history.lost, shows the *.orphaned-* file and stops.G3, G6
I6Every launch is verified against what it should give.nimitz reads the short id and Claude Code's notes ("started a copy as X"). A wrong id fails the step and removes the copy in the same plan. I7A by-hand action is reconciled, not refused.nimitz classifies each unlabelled session in a member's folder: a copy of the identity (same job, a fork whose transcript shares the identity's message uuids, or the identity's name) or a stowaway. start and sweep repair copies after one confirm. Each issue has one fix that works for its kind: a background session is stopped and removed; an interactive one is ended in its terminal (nimitz names the terminal); a live rename is fixed with /rename <expected>.G10, G12, G14, G15
I8A nimitz home acts only on sessions labelled for that home.Labels carry NIMITZ_HOME (they do already). A session labelled for another home is never an issue and never a fix target.G7

I10A by-hand session in a member's folder is told at once.The SessionStart hook gives an unlabelled session in a member's folder a short context: "this folder belongs to F/SQ/S; exit, or ask nimitz". It also records the session as an intruder for status. A stale row of a lead is history, not an error that blocks its ships.G4, G5, G12, G16

Parts of the design

  • Hook binder. The SessionStart hook writes the binding at once, under the registry lock (now it only logs). It uses source, the labels, the pid and the job id. SessionEnd records the reason per pid.
  • Job-keyed rows, labels per pid. The snapshot joins by job id, reads resumeSessionId, respawnFlags, name, nameSource, interactiveLineage, parkedJobId and spare, and keeps labels per pid.
  • Reconcile engine. One function turns the snapshot into actions: rebind, park, mark a copy, mark an intruder, mark a history loss. status shows the result; start and sweep apply the safe ones; check shows one working fix per issue.
  • Recovery by id. start and relaunch resume current by id for every role. -c is used only for an identity with an empty lineage, and the plan shows which transcript it will continue.
  • Verified launch. Every --bg step parses Claude Code's output; a copy note fails the step and removes the copy. A crash window gets a short wait.
  • Guard context. The SessionStart hook tells an unlabelled session in a member's folder who owns the folder.
  • Parking and revive. parked becomes a status. The commodore skill and Admiralty revive a parked ship before they send it work. nimitz up at login revives leads after a reboot.

Method, safety and clean-up

  • Four agents ran in parallel: by-hand CLI on a ship (cases 1 and 6), by-hand sessions and interactive leads (2 and 4), in-session commands and the environment (3 and 5), and a docs check (Claude Code docs: agent view, sessions, hooks, CLI reference).
  • Each test used a throwaway fleet (NIMITZ_E2E_*) with NIMITZ_HOME and NIMITZ_STATE in temp folders under ~/.cache/nimitz-e2e. The hooks of the test sessions wrote to the temp state. Interactive sessions ran in private tmux servers. The live HOME and MAIN sessions were not touched.
  • One harness problem was found and fixed during the run: a child claude kept the parent's CLAUDE_CODE_* values, and one test session took the name [HOME.GITHUB]-NIMITZ_DEV for about 40 s. nimitz wrote the right name back. This is gap G13.
  • One accidental print-mode session ran one turn in the repo folder and wrote four unlabelled hook lines to the live events file. It is harmless.
  • The org policy replaced the haiku model with Opus, so each test turn cost about $0.25. Turns were kept very short.
  • Not run: a real daemon stop, a reboot and a 60-minute idle wait (they would stop the live fleet or take too long; the log and the docs cover them); respawn --all; claude purge (it edits ~/.claude.json; simulated).
