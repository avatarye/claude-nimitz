Session mapping

claude-nimitz 0.3.1 on Claude Code 2.1.292 (it updated from 2.1.290 during the night) · 2026-10-07 · investigation only: nothing is implemented. Written in ASD-STE100 style, with the words of docs/design/cc-control-model.md §1.

Summary

  • We ran 38 cases on real Claude Code in a throwaway fleet. Result: 18 OK, 11 gaps, 8 breaks, 1 limit.
  • Ship lifecycle commands are safe: stop, kill, rm, respawn, attach and a native resume keep the same session id and the labels. The job row keeps the launch flags (respawnFlags).
  • The mapping breaks when the session id changes under a member (/clear, /resume, ←), when two processes share one id (claude -c next to a live lead), and when nimitz recovers a lead with -c. In these cases nimitz shows a live member as stopped, suggests a fix that stops the real member, or continues the wrong conversation.
  • Case 0: background members stop on their own after about one idle hour. The daemon retires them (bg retire <id>: idle-prompt, idle 61m). No SessionEnd hook fires. This stopped NIMITZ_DEV twice.
  • Root causes in nimitz: the registry moves only on a nimitz action; rows are keyed by session id, not job id; labels are kept per session id, not per process; leads resume with -c; leads started outside a nimitz pane never bind.
  • The design gives ten invariants (I1 to I10). The two most important: every session that starts with an identity's labels joins its lineage (the hook binds, by SessionStart source); and recovery continues the lineage current by id, never with -c.
  • Some gaps cannot be closed because Claude Code does not allow it: no hook can refuse a session, idle retirement has no setting, and a reboot does not respawn. The design detects these and repairs them.

How it works now

Claude Code and nimitz see a session in different ways. Claude Code keys everything by a session id. nimitz keys everything by an identity. The registry connects the two.

Claude Code: one process runs one session id. A job row (background only) can carry several session ids over time.

nimitz: the identity is fixed. The labels and the hooks connect a session to it. The snapshot reads Claude Code's files to find the live state.

Case 0: why a background ship stops on its own

NIMITZ_DEV stopped twice with a Stop line and no SessionEnd. The daemon log gives the cause:

[2026-10-05T07:09:01Z] [bg] bg retire 9aacf927: settled, idle 60m
[2026-10-06T02:18:02Z] [bg] bg retire 9aacf927: idle-prompt, idle 61m
[2026-10-06T02:18:02Z] [bg] bg settled 9aacf927 (done)
  • The daemon stops a background session that is idle at the prompt and not attached for about 60 minutes. The docs confirm it (agent view, "The supervisor process"). The conversation stays on disk.
  • No SessionEnd hook fires for it. The job row goes to done. nimitz shows the member as stopped, with no reason.
  • No setting, variable or flag changes the time. The documented opt-out is a pin (Ctrl+T in agent view). We found no file or command that sets the pin.
  • Other causes: a new binary restarts the daemon, but the daemon adopts the live workers (no stop). A crash restarts in about 15 s. A reboot stops all sessions, and they do not come back by themselves.
  • Recovery works today: nimitz start does a native resume with the same id (this session came back that way). The gap is that nothing does it automatically, and the status does not say why (G11).

Proposed design: one solid identity → session mapping

Goal: the identity is the only thing the user must know. A session is only the identity's current body. nimitz follows every body change, and it repairs every by-hand change, or tells the user the one step that repairs it.

invariantrulehow nimitz enforces or repairs itcloses
I1One identity has one lineage and one current session. Only the registry says which session is the identity.A name, the newest transcript and -c never decide it. All binds go through one writer under the registry lock. Each lineage entry records via: launch, resume, relaunch, clear, compact, fork, adopt or hook.G1, G3, G9
I2Every session that starts with an identity's labels joins that identity's lineage, whatever its SessionStart source.The SessionStart hook binds: startup and resume bind or confirm; clear and fork append and move current; compact confirms. If a hook line is lost, status replays the events under the lock. A lead binds the same way as a ship.G1, G5, G9
I3nimitz keys a background member by its job id, and it keeps labels per process.Join rows by session file jobId and job daemonShort. The live id is the session file sessionId or the job resumeSessionId; the job sessionId is only the launch id. A labelled pid is the member; an unlabelled pid on the same id is an intruder.G1, G2, G4
I4An identity has at most one live process, and a session id has at most one live process.Two live pids for one identity or one session id give dup.live with the exact terminal of each (the session file tmux or Herdr fields). nimitz never merges them.G4
I5Recovery continues the lineage current by its id.Leads and ships resume with --resume <current>; never -c. A resume that comes back with SessionStart startup is a history loss: nimitz raises history.lost, shows the *.orphaned-* file and stops.G3, G6
I6Every launch is verified against what it should give.nimitz reads the short id and Claude Code's notes ("started a copy as X"). A wrong id fails the step and removes the copy in the same plan. A job in the crash window (state crashed, or a dead pid on a working row) is given about 20 s to restart before nimitz resumes it.G8
I7A by-hand action is reconciled, not refused.nimitz classifies each unlabelled session in a member's folder: a copy of the identity (same job, a fork whose transcript shares the identity's message uuids, or the identity's name) or a stowaway. start and sweep repair copies after one confirm. Each issue has one fix that works for its kind: a background session is stopped and removed; an interactive one is ended in its terminal (nimitz names the terminal); a live rename is fixed with /rename <expected>.G10, G12, G14, G15
I8A nimitz home acts only on sessions labelled for that home.Labels carry NIMITZ_HOME (they do already). A session labelled for another home is never an issue and never a fix target.G7
I9Parked is a normal state.A member that the daemon retired, or that a reboot stopped, is parked: same id, no error. The commodore revives a parked ship (native resume, same id) before it signals it. nimitz up after login brings the leads back.G11
I10A by-hand session in a member's folder is told at once.The SessionStart hook gives an unlabelled session in a member's folder a short context: "this folder belongs to F/SQ/S; exit, or ask nimitz". It also records the session as an intruder for status. A stale row of a lead is history, not an error that blocks its ships.G4, G5, G12, G16

Parts of the design

  • Hook binder. The SessionStart hook writes the binding at once, under the registry lock (now it only logs). It uses source, the labels, the pid and the job id. SessionEnd records the reason per pid.
  • Job-keyed rows, labels per pid. The snapshot joins by job id, reads resumeSessionId, respawnFlags, name, nameSource, interactiveLineage, parkedJobId and spare, and keeps labels per pid.
  • Reconcile engine. One function turns the snapshot into actions: rebind, park, mark a copy, mark an intruder, mark a history loss. status shows the result; start and sweep apply the safe ones; check shows one working fix per issue.
  • Recovery by id. start and relaunch resume current by id for every role. -c is used only for an identity with an empty lineage, and the plan shows which transcript it will continue.
  • Verified launch. Every --bg step parses Claude Code's output; a copy note fails the step and removes the copy. A crash window gets a short wait.
  • Guard context. The SessionStart hook tells an unlabelled session in a member's folder who owns the folder.
  • Parking and revive. parked becomes a status. The commodore skill and Admiralty revive a parked ship before they send it work. nimitz up at login revives leads after a reboot.

Method, safety and clean-up

  • Four agents ran in parallel: by-hand CLI on a ship (cases 1 and 6), by-hand sessions and interactive leads (2 and 4), in-session commands and the environment (3 and 5), and a docs check (Claude Code docs: agent view, sessions, hooks, CLI reference).
  • Each test used a throwaway fleet (NIMITZ_E2E_*) with NIMITZ_HOME and NIMITZ_STATE in temp folders under ~/.cache/nimitz-e2e. The hooks of the test sessions wrote to the temp state. Interactive sessions ran in private tmux servers. The live HOME and MAIN sessions were not touched.
  • One harness problem was found and fixed during the run: a child claude kept the parent's CLAUDE_CODE_* values, and one test session took the name [HOME.GITHUB]-NIMITZ_DEV for about 40 s. nimitz wrote the right name back. This is gap G13.
  • One accidental print-mode session ran one turn in the repo folder and wrote four unlabelled hook lines to the live events file. It is harmless.
  • The org policy replaced the haiku model with Opus, so each test turn cost about $0.25. Turns were kept very short.
  • Not run: a real daemon stop, a reboot and a 60-minute idle wait (they would stop the live fleet or take too long; the log and the docs cover them); respawn --all; claude purge (it edits ~/.claude.json; simulated).
  • Clean-up: every test job is stopped and removed, every tmux server is killed, every test folder is removed. Transcript folders stay for you to delete:
